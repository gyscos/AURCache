## Goal
Give the dashboard a glanceable, action-oriented layout that answers "is the instance healthy and what happened lately?" without leaving the page, while keeping the existing `StatTiles` and `Builds per month` chart that already work.

## Success Criteria
- A user landing on `/` sees within one viewport: headline health (tiles), trend (chart), and what changed lately (recent packages, recent builds, recent activity) plus attention-needed slices (failed, long-queued, largest, longest) with links.
- Each new section loads independently (own `use_resource` + `use_poll`), shows a spinner on first load and an inline `alert-error` on failure, never blocks the other sections.
- Text, grid lines and chart follow the `daisyUI` theme (`oklch(var(--bc))` etc.) on `light`/`dark`/`system` and remain readable on `2560px` and `375px` widths.
- Server-side `order_by`/`filter` supplies meaningful ordering (recent, failed, largest, longest, queued) so the dashboard does not fetch 100 rows to sort 5 client-side; `limit=5` is enforced in SQL with indexes.
- All existing dashboard SSR tests continue to pass; new sections have `dioxus_ssr` unit tests and a browser smoke for links.

## Constraints And Non-goals
- **No fork of `dioxus-charts`:** theme/layout stay in `index.html` CSS as done for the chart fix; crate patch is not reintroduced.
- **Backend improvements are in scope when they surface more meaningful info or save work:** adding `?sort`/`?status` to `list_packages`/`list_builds` is preferred over shipping a card that sorts 100 rows client-side or shows the wrong "recent".
- **No heavy dashboard polling:** keep `use_poll(..., false)` slow tick, `limit=5` per section, no auto-refresh of logs every second.
- **Non-goals:** per-package build queue, worker detail, full log search, editable settings on the landing page, hover tooltips on the chart (crate has no hover props).

## Key Decisions
- **Layout: 1 + 1 + 2×2 + 1, responsive, still one viewport.** `StatTiles` (full width, 5 cards) → `Builds per month` (full width `h-64`) → `Recent packages | Recent builds` (`lg:grid-cols-2`) → `Failed | Out-of-date` and `Largest | Longest builds` (`lg:grid-cols-2` each, `N=3-5`) → `Recent activity` (full width). Keeps health/trend first, then "what changed", then "what needs attention", then narrative. Single column wastes `lg`; 3-col for the four attention cards is cramped for log lines.
- **Recent packages / builds / activity - all three.** They answer different questions: *what was added* (packages), *did it build* (builds), *what did the system do* (activity includes version checks/worker events). Each card gets its own `View all →` to its canonical list.
- **Server-side ordering/filtering, not client sort.** `list_packages` today is `order_by OutOfDate DESC, Id DESC` with no `?sort` (`package.rs:751-752`), `Id` is the only creation-order proxy and is hidden behind the `OutOfDate` primary sort. `list_builds` is `order_by start_time DESC` but has no `?status`/`?sort=size|duration`. Fetching 50 rows to sort 5 client-side is wasteful and still shows the wrong "recent" when `OutOfDate` bubbles old rows. Decision: add `?sort=recent|size` + `?status=failed|out_of_date` to `list_packages` and `?status=queued|failed` + `?sort=duration|size` to `list_builds`, with `limit` pushed to SQL (`LIMIT 5`) and indexed (`packages.id`, `packages.status`, `builds.start_time`, `builds.size`, `builds.peak_memory`, `builds.status`). Alternative client-side sort rejected for correctness and cost.
- **Cap at 5 (3 for Largest/Longest if denser) and link out.** Packages: `list_packages?sort=recent&limit=5&dependencies=false` (directly requested only, matches `StatTiles` headline). Builds: `list_builds?sort=recent&limit=5`. Failed/out-of-date: `list_packages?status=failed|out_of_date&limit=5`. Largest: `list_packages?sort=size&limit=5`. Longest: `list_builds?sort=duration&limit=5` (duration = `end_time - start_time` where `status` finished). Stuck queue: `list_builds?status=enqueued|waiting_for_deps&sort=queued_since&limit=5`. Keeps page < 2 viewports, queries are `LIMIT 5` indexed.
- **Empty/loading/error per card.** Each `use_resource` renders `loading-spinner` while `None`, `alert-error` on `Some(Err)`, muted `alert` on `Some(Ok([]))`. One failed section never blanks the rest.

## Recommended Approach
- Keep `Dashboard` as a `space-y-4` stack: `StatTiles` (`grid gap-4 grid-cols-2 lg:grid-cols-3 xl:grid-cols-5`), `BuildsChart` card (`chart-box h-64` + `oklch(var(--bc))` CSS), then a `grid gap-4 lg:grid-cols-2` holding `RecentPackagesCard` and `RecentBuildsCard`, then two `lg:grid-cols-2` rows for `FailedPackagesCard | OutOfDateCard` and `LargestPackagesCard | LongestBuildsCard` (`N=5`, `Largest` can be `3`), then `RecentActivityCard` full width. Each card is `card bg-base-100 shadow-xl` with `card-body` and `card-title text-base`, matching `StatTile` and the chart card.
- Each new card is a small `#[component]` with its own `use_resource(|| client.list_*(...))` and `poll::use_poll(resource, false)` slow tick. Titles: "Recent packages" → `Route::Packages`, "Recent builds" → `Route::Builds`, "Failed" / "Out of date" / "Largest" → `Route::Packages` with the matching filter, "Longest builds" / "Stuck queue" → `Route::Builds`, "Recent activity" → `Route::Logs`. Header row `flex justify-between items-baseline` with title left and `Link { class: "link link-primary text-xs", "View all →" }` right.
- **Recent packages rows:** `SimplePackage` name via `PackageBadge` pattern (`screens/packages.rs`), status dot via `BuildStatusBadge`, row is `Link` to `Route::Package { pkgbase }`. Uses `list_packages?sort=recent&limit=5&dependencies=false`. Empty: "No packages yet. Add one →".
- **Recent builds rows:** `Build` `pkgbase`, `#number`, `BuildStatusBadge`, `version`, `AbsoluteDate` (`start_time`), row links to `Route::Build { pkgbase, number }` (`status::BuildStatusBadge` in `screens/builds.rs`). Uses `list_builds?sort=recent&limit=5`.
- **Attention rows:** `Failed` (`list_packages?status=failed`), `OutOfDate` (`?status=out_of_date`), `Largest` (`?sort=size`, `SimplePackage.total_size` via `total_artifact_size_expr()` in `package.rs:750`), `Longest` (`list_builds?sort=duration`, `duration = end_time - start_time` where `end_time` not null, `builds.rs:22-36`), `Stuck` (`list_builds?status=enqueued|waiting_for_deps&sort=queued_since`). Each shows the natural secondary value (size `format_bytes`, duration `format_secs`, queued `AbsoluteDate`).
- **Recent activity rows:** `log(Some(5), None, ..)`, each row `flex gap-2` with `Severity` badge (`badge badge-info` etc.), `AbsoluteDate`, and the entry rendered as the Logs page renders it (`EntryText` in `screens/logs.rs`): each entity its sentence names is a `Link`, and an entry that does not decode falls back to its stored `message`.
- **Styling:** muted `opacity-60`, dividers `divide-y divide-base-200`, rows `py-2 flex justify-between`, cards `shadow-xl`. Chart stays `chart-box h-64` with existing themed CSS.

## Risks / Rollback
- **New `?sort`/`?status` adds query surface:** risk of unindexed `ORDER BY size`/`duration` or SQL injection via stringly sort. Mitigation: whitelist `sort` enum (`recent|size` for packages, `recent|duration|size` for builds) and `status` enum, map to fixed `order_by`/`filter` branches, keep `LIMIT 5` and rely on existing `packages.id`/`builds.start_time` indexes plus `total_artifact_size_expr()` already indexed via `files` sum; add `EXPLAIN` check in review. Rollback is to remove the new `match` arms and fall back to current `OutOfDate, Id` / `start_time` ordering - dashboard cards then show the old ordering, no data loss.
- **Seven extra concurrent fetches on landing:** risk slower first paint. Mitigation: `limit=5`, `use_poll(false)` slow tick, and cards render independently so chart/tiles not blocked. Rollback is to hide the `Largest`/`Longest`/`Stuck` row behind a flag, keep `Recent` trio.
- **Activity prose length:** long `text` could wrap and push layout. Mitigation: `line-clamp-2` + `truncate` on subject, keep row `min-h` consistent.
